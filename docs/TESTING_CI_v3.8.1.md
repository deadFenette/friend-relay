# Тесты и CI (v3.8.1)

Как устроена проверка стабильности friend-relay: что гоняется локально,
что гоняется в CI, и как добавлять новое.

## Три слоя проверки

1. **Модульные/интеграционные тесты** — `tests/test_*.py` (50+ файлов,
   ~1600 проверок). Каждый файл — самостоятельный скрипт: сам поднимает
   `RelayServer` на loopback (или трогает доменные классы напрямую),
   печатает `[OK]/[FAIL]` и завершается кодом 0/1. Никаких pytest/unittest
   фреймворков — проще запускать и читать.

2. **Браузерные E2E** — `scripts/web_*_e2e.py`: Chromium (playwright),
   фантомные сессии, реальные скриншоты. Требуют дисплей/Xvfb, поэтому в
   CI НЕ гоняются — только локально/на машине с графическим окружением.

3. **Stability-прогон** — `tests/test_stability_v381.py` (v3.8.1):
   сервер обязан переживать грязь. Пять блоков:
   - **A. Грязный HTTP** — мусорные байты, битый JSON, враньё в
     Content-Length, обрыв тела, 16КБ URL, шапка-бомба: сервер жив.
   - **B. Битый журнал** — обрезанная последняя строка, мусор в середине,
     валидные НЕ-dict JSON-строки: загрузка без краха, seq не откатывается.
   - **C. Гонки** — 100 параллельных сообщений (уникальность seq), микс
     send/edit/delete без 5xx, параллельные upload, poll под нагрузкой.
   - **D. Рестарт** — close->reopen EventStore, stop->start RelayServer:
     данные целы, seq продолжается.
   - **E. Границы файлов** — сервер с ключом и max_file_size=1024: 413 на
     превышение, пустой/отрицательный Content-Length, обрыв потока без
     .part-хвостов, враньё в sha256, мусорная подпись -> 403, честная
     HMAC-подпись -> 200.

## Авто-раннер: scripts/run_all_tests.py

Кроссплатформенная замена `scripts/run_regression.sh` (sh-версия осталась
для совместимости):

```
python scripts/run_all_tests.py              # весь headless-регресс
python scripts/run_all_tests.py --list       # показать план прогона
python scripts/run_all_tests.py --only voice # по подстроке имени
python scripts/run_all_tests.py --skip stability --timeout 120
python scripts/run_all_tests.py --ci         # компактно + аннотации GitHub
```

Что даёт:
- **пер-тестовый таймаут** (по умолчанию 300с): зависший тест убивается с
  пометкой TIMEOUT, а не замораживает весь прогон;
- нормализацию сводок (`PASS=N`/`N OK`/`Итого`) в общий итог;
- код возврата 1 при любом FAIL — годится и для CI, и для хуков;
- `--ci`: аннотации `::error file=tests/...` видны прямо в PR.

По умолчанию пропускаются тесты, требующие дисплей/аудио/Windows:
`test_qt_*`, `test_v195_qt.py`, `test_legacy_live*` — та же политика,
что в `run_regression.sh`.

## CI: .github/workflows/ci.yml

GitHub Actions: на каждый push/PR в `main` — два джобы Python 3.11 и
3.12 на ubuntu-latest:

1. `pip install urllib3 orjson cryptography numpy websockets mutagen` —
   «полный безголовый» набор из requirements.txt БЕЗ PySide6 (GUI),
   sounddevice (PortAudio+устройство) и opuslib_next (libopus): без них
   приложение честно деградирует, и эти fallback-пути покрыты тестами.
2. `python -m compileall -q lib voice scripts tests` — быстрый синтакс-гейт.
3. `python scripts/run_all_tests.py --ci` — весь headless-регресс,
   включая stability-прогон.

Ветка в бейдже README: статус последнего прогона main.

## Как добавлять тест

- Новый файл `tests/test_<тема>_v<версия>.py`, стиль — как в
  `test_stability_v381.py`/`test_convenience_v380.py`: `check(name, cond)`,
  счётчики PASS/FAIL, `main() -> int`, `sys.exit(1) if FAIL`.
- Поднимайте сервер на свободном порту (`free_port()` из stability-теста),
  а не на «магических числах» — иначе конфликты с остаточными процессами.
- Раннер подхватит файл автоматически (glob `tests/test_*.py`) —
  ничего регистрировать не нужно.
- Тест НЕ должен требовать дисплей/аудио — иначе пометьте его в
  DEFAULT_SKIP раннера и в skip-списке run_regression.sh.

## SKIP: зависимости сверх безголового набора (CI-fix)

Первый же прогон CI показал две проблемы, и обе починены:

1. `test_web_images_v368.py` требует playwright (браузерный E2E), а CI
   браузер не качает — CI должен оставаться быстрым и детерминированным.
   Решение двухуровневое: раннер получил карту `TEST_NEEDS`
   (имя файла → модули) — при отсутствии модуля тест помечается SKIP
   (не FAIL, в итог не идёт, в конце выводится `[SKIP] имя: нет модуль`);
   а сам тест при прямом запуске без playwright больше не падает
   ModuleNotFoundError, а честно завершается 0 с подсказкой, как
   поставить зависимости для локального прогона.
2. `test_web_voice.py` падал на CI гонкой: сервер отклоняет «плохого»
   клиента и прибывает соединение так быстро, что клиентский `send()`
   ловит ConnectionClosedError раньше, чем успевает прочитать ошибку.
   Проверка «неверный ключ отклонён» теперь принимает ОБА варианта
   отказа: внятную ошибку ИЛИ обрыв соединения — семантика та же
   (клиент не пущен), а поведение машины больше не влияет.

Браузерные E2E (scripts/web_*.py и tests/test_web_images_v368.py)
по-прежнему гоняются локально/на релизе: там есть Chromium.

## Харденинг тайминговых тестов: test_bridge_hb_v365 (CI-fix, раунд 2)

Второй прогон CI: 3.11 зелёный целиком, на 3.12 один раз упал
`test_bridge_hb_v365.py` (микшерный heartbeat-тест с живым сервером).
Локально (включая Python 3.12 и искусственное голодание CPU) тест
стабильно зелёный — классический флак медленного раннера. Причины:

- жёсткие окна ожидания 1.5-2.0с: под нагрузкой echo/pong приходят
  позже окна, а порог «binary > 20 кадров» в фиксированном 2с-окне
  режется деградацией тик-потока микшера (под голоданием кадров втрое
  меньше: 151 → 49);
- `drain()` ловил только `asyncio.TimeoutError`: если сервер закрыл
  соединение, `ws.recv()` бросал ConnectionClosed сквозь пробу — тест
  умирал исключением с голым rc=1 без указания проверки.

Что сделано (семантика всех 12 проверок НЕ изменена):

- окна расширены: auth 1.5→3с, hb-echo 1.5→3с, аудио-фаза 2→6с,
  pong 2→4с; при этом добавлены РАННИЕ ВЫХОДЫ из drain по условию
  (roster/echo/pong пойманы, кадров >= 30) — на быстрой машине тест
  стал быстрее прежнего (~2.5с вместо ~7с), на медленной — добирает
  кадры до дедлайна вместо среза;
- drain ловит закрытие соединения как СОБЫТИЕ (печатает причину),
  а не как необработанное исключение;
- краш пробы целиком превращается в именованный FAIL с трейсбеком —
  следующий флак в CI будет сразу виден с местом и причиной;
- старт сервера ретраится на свежем порту (гонка TOCTOU у free_port).

Урок для будущих тайминговых тестов: не «ждать N секунд и проверить
порог», а «ждать ДО условия с запасным дедлайном»; любое исключение из
живой пробы — это недостаток теста, а не продукта.

## Раунд 3: НАСТОЯЩИЙ корень — CI жил на websockets 17 (вне заявленной поддержки)

Харденинг раунда 2 помог (3.12 позеленел), но 3.11 флакнул на ДРУГОМ
тесте (test_web_voice, свежее WS-соединение прибито между рукопожатием
и первым send: SSLEOFError -> ConnectionClosedError). В логе нашлась
настоящая причина ВСЕХ этих флаков:

    Downloading websockets-17.2-cp311...

Строка установки в ci.yml ставила websockets БЕЗ границ версий, а
requirements.txt требует `>=12.0,<17` (мажор 17 не заявлен: другая
семантика закрытия соединений). Локально стоит 16.0 — сотни прогонов
без единого флака; все три CI-прогона шли на 17.2. Классический
«работает у меня»: различие не в коде, а в зависимостях окружения.

Сделано:

1. ci.yml: все пакеты headless-набора ставятся С ГРАНИЦАМИ из
   requirements.txt (urllib3<3, orjson<4, cryptography<48, numpy<3,
   websockets<17, mutagen<2). Правило на будущее: CI == заявленному
   окружению, пин синхронизируется при бампе требований.
2. tests/test_web_voice.py: хелпер ws_connect_auth() — connect + auth +
   первый ответ с одним ретраем СВЕЖИМ соединением (гонка окружения
   «туннель × медленный раннер», не продукта). Применён к обоим свежим
   соединениям (web и listener); проверяемый факт подтверждается на
   успешной попытке; обе попытки убиты — AssertionError с причиной.
3. tests/test_bridge_hb_v365.py: тот же ретрай для первичного
   connect+auth пробы (до этого краш был уже превращён в именованный
   FAIL с трейсбеком — раунд 2).
4. scripts/run_all_tests.py: в --ci упавший тест перезапускается ОДИН
   раз (--retries, по умолчанию 1 в CI / 0 локально). Детерминированный
   фейл падает и на ретрае (остаётся красным); случайный зеленеет —
   честно, с пометкой «ретрай» в строке результата и в логе.

Проверено симуляцией: тест «падает 1-й раз, зелёный на 2-м» ->
OK <ретрай 1>; тест «падает всегда» -> FAIL и после ретрая.

# Производительность: что сделано и что можно улучшить (v9.3 + v2.0.2 + v2.0.4)

Контекст: chat_screen «тупил» при переключении каналов и мог зависать.
Ниже — что уже исправлено в v9.3, v2.0.2 (ядро сервера) и v2.0.4 (новые
utility ядра) и дальнейшие предложения. Все рекомендуемые библиотеки — с
пермиссивными лицензиями (MIT/BSD/Apache-2.0), совместимыми с закрытым и
открытым использованием.

## Что сделано в v2.0.4 (новые utility ядра)

| Горячая точка | Решение | Где | Эффект |
|---|---|---|---|
| Повторная ссылка в чате = повторная закачка страницы для превью (секунды сети, трафик, поток из семафора на каждое сообщение) | `lib/util.TTLCache` — кеш превью по URL на 10 минут (LRU-вытеснение, кешируются только успешные результаты) | `lib/link_preview.py` (`_PREVIEW_CACHE`) | повторный URL — 0 закачек и 0 сетевых потоков; правки страницы подхватываются через 10 минут |
| Флуд в /send_text или /dm/send: сотни сообщений в секунду жгут CPU хоста, диск JSONL и сеть поллящих клиентов | токен-ведро на отправителя: `util.TokenBucket` + `util.RateLimiter` (LRU, max 512 вёдер), политика — `RelayServer.allow_message()` | `lib/util.py`, `lib/relay_server.py`, `lib/server/http_api.py` (`/send_text`, `/dm/send` -> 429 + `retry_after`) | всплеск живого человека (30 мгновенных) не задет; скриптовый флуд режется до записи в журнал |
| Нет наблюдаемости «как дышится серверу»: uptime в секундах, латентность не видна вовсе | `util.LatencyMeter` (счётчик + окно 256 замеров, avg/p95); замер в безопасных обёртках do_GET/do_POST; `util.fmt_uptime` | `lib/server/http_api.py` (замер), `lib/relay_server.py` (`note_request`, поля stats) | `GET /server/stats`: `requests_total`, `avg_ms`, `p95_ms`, `uptime_human`, `flood_buckets` — деградация видна до того, как её заметят в чате |

Замечания к совместимости v2.0.4: WS-туннель голоса исключён из замера
(`_skip_meter`) — «минутные» латентности туннеля не портят p95 обычных
запросов; ответы ботов идут через фасад, а не через HTTP-маршруты, поэтому
антифлуд их не задевает; новые поля /server/stats аддитивны — существующие
потребители (веб-профиль, curl) не ломаются.

| Горячая точка | Решение | Где | Эффект |
|---|---|---|---|

Замечания к совместимости: JSON-ответы теперь компактные (без пробелов

сравнивают байты). Регресс: новый `tests/test_core_v202.py` (49 проверок),
весь старый headless-набор зелёный; ruff 0.

| Проблема | Решение | Эффект |

## Предложения дальше (по убыванию пользы)

### 1. Виртуализированный список сообщений (QListView + делегат)

Сейчас каждый виджет сообщения — это ~10-15 дочерних QWidget'ов. При
длинных лентах это упирается и в память, и в скорость прокрутки, а
`MAX_RENDERED_ROWS` приходится держать ограничением.

Правильное долгосрочное решение — модель/вид Qt:

- `QAbstractListModel` поверх хвостов из `ChatSession` (ядро уже без Qt —
  хорошо ложится);
- кастомный `QStyledItemDelegate` рисует бабл через `QPainter` (текст —
  `QTextDocument`, картинки — pixmap-кэш);
- виджет создаётся только для ВИДИМЫХ строк — прокрутка тысяч сообщений
  остаётся плавной, память константная.

Сторонних библиотек не требует — это штатный путь Qt. Оценка: самый
трудоёмкий пункт (переписывается рендер), зато снимает потолок истории
и делает «Показать» из пинов возможным для любого seq (сейчас лента
держит только хвост). Можно делать поэтапно: сначала только для каналов.

### 2. orjson вместо json (лицензия MIT) — СДЕЛАНО в v2.0.2

Реализовано: `lib/json_fast.py` — тонкая обёртка (loads/dumps/dumps_str)
с автоматическим фолбэком на stdlib, подключена в транспорте
(`_send_json`/`_parse_json`) и домене (`_append_event`). orjson —
опциональная зависимость (`pip install orjson`, см. requirements.txt):
без неё сервер работает на stdlib, просто медленнее. Бэкенд виден в
`GET /server/stats` (поле `json_backend`).

### 3. Push-обновления вместо поллинга (SSE или WebSocket)

Сейчас клиент опрашивает `/events?since=` раз в секунду: латентность
доставки сообщения в среднем 500 мс, плюс постоянный фон из запросов.
Сервер уже держит WebSocket-мост для голоса (`tls_mux` туннелирует WSS) —
то есть инфраструктура для push уже есть.

Варианты:

- **SSE** (Server-Sent Events) поверх существующего HTTP-сервера —
  минимум нового кода, автопереподключение из коробки, работает через
  тот же keep-alive пул;
- **WebSocket** (`websockets` уже в зависимостях, лицензия BSD-3).

Эффект: мгновенная доставка (нет ожидания тика), пауза поллинга →
ниже CPU и батареи на обоих концах. Поллинг оставить как fallback
(сейчас архитектура ядра `ChatSession` позволяет подменить источник
события — колбэки уже отделены от транспорта).

### 4. Полнотекстовый поиск по истории — SQLite FTS5 (stdlib, без зависимостей)

Поиск сейчас работает только по загруженной ленте (последние ~50-400
сообщений). `sqlite3` уже в stdlib, FTS5 — его часть: таблица
`messages(seq, channel, text)` + `FTS5-индекс`, наполнение — при записи
на сервере, запросы — через тот же HTTP API. Это снимет ограничение
«поиск только по загруженному» без сторонних библиотек.

### 5. markdown-it-py вместо самописного рендера (лицензия MIT)

`lib/markdown_renderer.py` — самописные regex'ы подмножества Markdown.
Для роста фич (списки, таблицы, вложенность, автоссылки по CommonMark)
надёжнее взять `markdown-it-py` (MIT, порт эталонного markdown-it,
~сотни КБ, без нативных зависимостей): включить `linkify` для ссылок,
XSS-безопасность сохранить через существующее экранирование + белый
список тегов в QLabel. Интеграция точечная (одна функция), но выигрыш —
не скорость, а корректность и покрытие синтаксиса. Скорость текущего
рендера достаточна (вызывается только для сообщений с разметкой).

### 6. Мелкие точки роста (без новых зависимостей)

- **`QLabel` бабла**: для длинных сообщений `QTextBrowser` с
  `setOpenExternalLinks(False)` дешевле пересчитывается при ширине
  ленты; плюс исчезнет двойное форматирование markdown → HTML → rich text.
- **Пины/каналы**: `_on_channels_loaded` пересоздаёт все pill'ы — можно
  диффить по имени (по аналогии с чипами онлайна); нагрузка мала, делаем
  по мере роста числа каналов.
- **Сервер**: `/events` можно отдавать `orjson.dumps(...,
  opts=orjson.OPT_SERIALIZE_DATETIME)` и добавить ETag/304 на неизменный
  курсор — экономия трафика на холостых тиках (сейчас ответ всегда
  непустой из-за online/typing).
- **Профилирование под нагрузкой**: прогонять
  `scripts/bench_channel_switch.py` и серверный смок с логом 10⁵+ событий
  перед релизами — дёшево и ловит регрессии заранее.

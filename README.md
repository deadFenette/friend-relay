Friend Relay — простой чат + отправка любых файлов через твою же
приватную сеть (ZeroTier / Tailscale / Porthole).

ЧТО ЭТО
-------
Отдельная программа, не связанная с Minecraft-сервером и раздачей модов
(хотя работает по той же идее и по тому же tailnet-адресу). Позволяет:
  - переписываться простыми текстовыми сообщениями;
  - слать друг другу ЛЮБЫЕ файлы (фото, архивы, что угодно) - не только
    моды;
  - писать личные сообщения (ЛС) отдельным диалогом;
  - управлять ботами для автоматических действий.
История сообщений и файлы хранятся у ХОСТА (тот, кто держит "Я хост"
включённым) - на диске в папке
  Windows: C:\Users\<имя>\.friend_relay\relay_data\
и переживают перезапуск программы.

КАК ЗАПУСТИТЬ
-------------
Дважды кликни `RUN.bat` или запусти `python main_qt.py` (Python + PySide6).

ОДИН ЧЕЛОВЕК ДОЛЖЕН БЫТЬ ХОСТОМ
--------------------------------
1. Тот, у кого стабильно работает ZeroTier/Tailscale/Porthole (обычно
   тот же человек, что держит менеджер Minecraft-сервера) - ставит
   галку "Я хост", указывает порт (по умолчанию 8420) и жмёт
   "Подключиться".
2. Остальные - снимают галку "Я хост", вписывают адрес хоста в формате
       http://<tailnet-ip-хоста>:8420
   (тот же IP, что вы уже используете для раздачи модов) и жмут
   "Подключиться".
3. Все могут писать сообщения и слать файлы друг другу - хост просто
   пересылает всё между всеми подключёнными, включая себя.

Если хост выключит программу - раздача останавливается для всех до
следующего его запуска. История при этом никуда не девается (лежит на
диске у хоста).

КАК СТАТЬ АДМИНОМ
-----------------
Модель простая: АДМИН = ЛИЧНОСТЬ ХОСТА. Админ — это не «галочка», а
клиент, чьё имя совпадает с именем хоста сервера (--name / настройки
GUI). Имя хоста зарезервировано: гость, введя его, получает «Имя#2»
(как дискриминаторы в Discord). Что даёт админство:
  - управление music-ботом, когда open_dj выключен (!music dj off);
  - приоритетная личность: твоё имя никто не украдёт;
  - будущие админ-действия из веба (роадмап P1/P2).

Три способа стать админом:
  1. С МАШИНЫ ХОСТА — само. Qt-клиент/GUI, запущенные на той же машине,
     где работает сервер, входят под именем хоста без ключа (loopback).
  2. С ДРУГОГО УСТРОЙСТВА (веб): в веб-клиенте введи ИМЯ ХОСТА в поле
     «Твоё имя» и КЛЮЧ в поле «Ключ админа». Ключ печатает сервер при
     старте (шпаргалка «Admin key») и показывает GUI хоста (кнопка
     «Копировать» рядом с «Ключ админа»). Ключ живёт в
     relay_data/admin_key.json и переживает рестарты.
  3. ЧЕРЕЗ КОМАНДУ/БАТНИК (сервер без GUI):
       python server_main.py --name Василиса --admin-key ВАСИЛИСА_2014_ХХХ_КАРА_НЕБЕСНАЯ
     Ключ из --admin-key сохраняется в relay_data/admin_key.json —
     на следующих запусках флаг можно не повторять. Или просто
     RUN_SERVER.bat (имя/ключ/порт редактируются в шапке файла).
     Удобно задать СВОЙ запоминающийся ключ один раз — и вводить его
     в вебе на телефоне/планшете.

ВАЖНО (одна личность = одна живая сессия): если войти админом в вебе,
сессия Qt-клиента/приложения с ТЕМ ЖЕ именем аннулируется (вылетит),
и наоборот — это защита от перехвата (v3.3.1). То есть «сижу в Qt-
клиенте хостом И админом в вебе» одновременно не выйдет: либо открой
веб под обычным гостевым именем, либо отключай Qt-клиент, когда
управляешь сервером из веба.

Не принято, а потом непонятно почему: если ключ введён неверно, сервер
НЕ выгоняет, а выдает «Имя#2» и помечает ответ (admin_key_rejected) —
веб покажет «Ключ админа НЕ ПРИНЯТ». Проверь ключ и что имя в поле
«Твоё имя» в точности совпадает с именем хоста.

БРАУЗЕР БЕЗ УСТАНОВКИ (ОДИН АДРЕС НА ВСЁ)
-----------------------------------------
Друг может открыть не приложение, а просто браузер: хост даёт ОДИН адрес
    https://<tailnet-ip-хоста>:8420
Порт тот же, что у приложения - никаких 8423/8424 переключать не нужно
(TLS и обычный HTTP живут на одном порту). При первом заходе браузер
покажет предупреждение про самоподписанный сертификат - «Дополнительно»
→ «Перейти на сайт», один раз. Дальше: чат, файлы, шахматы и вкладка
«🎙 Голос» (микрофон работает только по https - поэтому адрес именно
такой). В приложении (Qt) адрес по-прежнему http://IP:8420.

КЛЮЧ ДОСТУПА (НЕОБЯЗАТЕЛЬНО)
-----------------------------
Раз твоя сеть приватная (только ты и друзья в ZeroTier/Tailscale), это
уже сама по себе защита - посторонний физически не достучится до порта.
Но если хочешь дополнительный барьер (на случай, если у кого-то в
tailnet есть посторонние устройства) - хост вписывает любое слово в
поле "Ключ доступа", и просит всех друзей ввести точно такое же перед
подключением. Без него - не подключатся.

ЧТО ЕСТЬ В ИНТЕРФЕЙСЕ
---------------------
- Система вкладок:
  * Общий чат - все сообщения для всех участников
  * ЛС - личные сообщения в отдельных диалогах
  * Боты - управление ботами на сервере
- Обычный вид чата - пузыри сообщений (свои справа акцентным цветом,

АВАТАРКИ И PILLOW
------------------
Показывать ЧУЖИЕ аватарки можно всегда, из коробки, ничего ставить не
надо. А вот чтобы поставить СВОЁ фото, нужна библиотека Pillow (обрезать
фото в круг средствами одного только Tkinter неудобно) - она специально
не входит в комплект по умолчанию, чтобы прогу можно было просто
запустить без доп. установок. Если хочешь своё фото:
    pip install Pillow
и перезапусти программу. Без неё всё остальное (чат, файлы, чужие
аватарки) работает как обычно - просто у тебя будет цветной кружок с
буквой вместо фото.

БЫСТРОДЕЙСТВИЕ
---------------
- При заходе показываются только последние 60 сообщений истории, а не
  вся она разом - подключение не подвисает даже если чат идёт неделями.
- Список сообщений в окне не растёт бесконечно - старые (за пределами
  примерно 400 последних) просто убираются из ОТОБРАЖЕНИЯ, на хосте
  ничего не удаляется.
- Пачки новых сообщений (например, после недолгого обрыва связи)
  отрисовываются одним заходом, а не по одному - раньше на каждое
  сообщение шёл отдельный принудительный пересчёт разметки окна.
- Виртуализация списков (боты, диалоги) для быстрой работы с большими
  данными.

БОТЫ
----
Боты позволяют автоматизировать действия в чате. Для добавления бота:
1. Хост запускает раздачу (вкладка "Боты" станет активной)
2. В поле "ID бота" вводишь имя (например, night_shift)

1. Создай файл lib/<имя>_bot.py (например, lib/my_bot.py)
2. В нём класс <Имя>Bot, наследующий от BaseBot
3. Реализуй методы handle_message и optional методы
4. Бот автоматически появится в списке доступных

GUI-ПОТОК И PySide6: почему окно «любит» отдельный поток (урок v3.4.2)
-----------------------------------------------------------------------
Короткий ответ на вопрос «это из-за того, что это PySide6?» — НЕТ,
это не особенность PySide6. В ЛЮБОМ GUI-фреймворке (Tkinter, GTK, wx,
Qt, Electron, WinForms...) окно живёт, пока крутится главный цикл
событий (event loop): именно он обрабатывает клики, перерисовку,
таймеры и анимации. Если главный поток занят чем-то долгим (диск,
сеть, генерация ключа TLS) — цикл останавливается и окно «Не отвечает».
Это устройство всех GUI, а не баг Qt.

Почему PySide6 КАЗАЛОСЬ причём тут — три его особенности:
1. У Qt виджеты имеют «привязку к потоку» (thread affinity): трогать
   QWidget из чужого потока ЗАПРЕЩЕНО — краш или тихие глюки. Поэтому
   фоновый поток не может сам обновить экран, только через сигналы.
2. Отсюда ощущение, что «GUI-поток очень любит быть отдельным» — так
   и есть: вся тяжёлая работа должна жить в фоновых потоках и
   возвращаться в GUI через сигналы (у нас это qt_app/async_bridge.py
   и класс _Worker в server_gui.py).
3. Tkinter, кстати, страдает тем же (всё из главного потока), просто
   он молча подвисает, а Qt ещё и ругается/падает при нарушении —
   поэтому в Qt это заметнее и... правильнее.

Что именно блокировало GUI-поток в v3.4.1 (полный разбор в docs/):
- RelayServer(...) + relay.start() вызывались ПРЯМО в слоте кнопки Qt;
- генерация TLS-сертификата RSA-2048 — 84.6 секунды на слабом CPU;
- getaddrinfo()/connect() без таймаутов — вечное ожидание при VPN;
- MusicBot писал music_data.json на диск ПОД ЛОКОМ — из-за этого все
  /music/sync (опрос каждые 200мс) и кнопки плеера ждали диск.

Как теперь: тяжёлое — в фон через _Worker/AsyncBridge, музыкальный бот
пишет на диск с дебаунсом (и флашем при остановке), сеть — строго с
таймаутами, сертификат — ECDSA P-256. Правило на будущее: в слотах Qt
(функции-обработчиках кнопок/сигналов) НЕЛЬЗЯ делать сетевые/дисковые
операции напрямую — только через фоновый поток + сигнал обратно.

ДОПОЛНИТЕЛЬНЫЕ ВОЗМОЖНОСТИ
---------------------------
- Реальный прогресс и скорость при отправке/скачивании файла (не просто
  "крутилка" - видно "43%  1.2МБ/с"). Специально для тех, у кого канал
  не быстрый - чтобы было видно, что оно вообще идёт, а не зависло.
- "🟢 На связи: ..." под шапкой - кто из друзей сейчас держит программу

- "Автоподключение при запуске" - галка, чтобы не подключаться каждый

- Если свернул/переключился с окна, а тебе написали - звуковой сигнал и
  "●" перед заголовком окна (пропадает, как только вернулся в окно).
- "Лимит файла (МБ)" - у хоста в настройках, не в коде: сам решаешь,
  сколько разрешать заливать одним файлом.
- Контекстные меню на сообщениях (копировать, ответить, удалить)
- Подгрузка старых сообщений при скролле вверх
- Проверка обновлений при запуске (опционально)

О СКОРОСТИ ДЛЯ ТЕХ, У КОГО РЕЖУТ МОБИЛЬНЫЙ ИНТЕРНЕТ
-----------------------------------------------------
Если у друга браузер/скачивание тормозит, а игры по тому же ZeroTier/
Tailscale летают нормально - это обычно значит, что оператор режет
именно РАСПОЗНАННЫЙ HTTP-трафик (по DPI видно "это скачивание файла"),
а зашифрованный VPN-туннель ему не прочитать - для оператора что игра,
что файл через тот же туннель выглядят одинаково, просто поток байт до
пира. Раз игры через тот же тоннель уже летают - эта программа, скорее
всего, унаследует ту же "льготу", потому что идёт по тому же самому
туннелю. 100% гарантии нет (бывают операторы, которые режут вообще
любой нераспознанный/VPN-трафик отдельно) - но раз одно уже работает,
велика вероятность, что заработает и второе. Проверяется тупо одной
отправкой файла.

## v2.0.0 (v10.0) — голос переписан: отдельный модуль voice/, fullband 48 кГц, абсолютный такт микшера

### Диагноз: почему звук был «пиздец ужасный» (4 корня)

- **ДРЕЙФ ТАКТА МИКШЕРА (главный виновник).** Цикл микширования
  выравнивал каждый тик ОТНОСИТЕЛЬНО предыдущего: `sleep(0.01 - elapsed)`.
  time.sleep всегда спит чуть дольше запрошенного — запаздывание
  НАКАПЛИВАЛОСЬ, микшер разбирал не 100 кадров/с, а меньше, входные
  очереди переполнялись, и каждые несколько секунд выбрасывалось по
  60 мс речи (дроп до пребуфера). На Windows дрейф сильнее. На слух —
  «прожёвывание» и робот-голос у ВСЕХ участников. В песочнице на Linux
  таймер точнее — поэтому автотесты были зелёными, а живой звук — нет.
- **Плейаут клиента — `deque(maxlen=200мс)`:** при всплеске TCP молча
  выкидывал самые старые кадры по одному; воспроизведение начиналось с
  первого же кадра без пребуфера — дыры, щелчки, фейд-ины на каждом
  затишье.
- **16 кГц «телефонный» звук + жёсткий шумовой гейт** (медиана RMS
  за окно × 2): во время непрерывной фразы медиана = уровень самой речи,
  и любой провал между слогами оказывался ниже порога и ЗАМЕНЯЛСЯ
  НУЛЁМ — слова «обкусаны».
- **Opus в режиме AUDIO 32 кбит/с без FEC/PLC** — на бурстах дыры
  не прикрывались ничем, PLC микшера — затухающий повтор слога.

### Что сделано

- **АРХИТЕКТУРА: голос вынесен в самодостаточный пакет `voice/`**
  (ноль импортов из lib/ — только stdlib + numpy/sounddevice/

  тюн-константы в одном месте), `codec.py`, `dsp.py` (RMS/high-pass/
  soft gate/PLC/микс), `devices.py` (сейм sounddevice для тестов),
  `mixer.py`, `bridge.py`, `client/` (engine + capture + playback).

- **ЗВУК: 48 кГц fullband + кадры 20 мс** (стандарт Discord/WhatsApp):
  вдвое меньше кадров в секунду — меньше оверхеда TCP и джиттера;
  приемник ОС почти всегда нативно 48к — лишний ресемпл исчез.
- **МИКШЕР: абсолютный такт** — сколько 20мс-кадров прошло с старта,
  столько тиков и выполняется (шкала perf_counter); отставание в 1-2
  кадра догоняется пачкой, необратимое — ресинхронизация без «взрыва».

- **КОДЕК: Opus VOIP 48 кбит/с + inband FEC** (скелет предыдущего

- **КЛИЕНТ: нормальный джиттер-буфер** (`voice/client/playback.py`):

## v1.9.8 (v9.10) — чистый голос: Opus вместо самописного звука + стабильность

**Задача: «короче проблемы с ГС. Когда говоришь — шумит белыми помехами.
Типо поговорил — белые помехи, закончил — белые помехи (затухающие).

**ФИКС (критично, Qt): белые помехи на концах фраз.** Источник найден —
это был СОБСТВЕННЫЙ «comfort noise» клиента: silence-кадры, которые
микшер рассылает в паузах (0.5с после последнего голоса), заменялись
белым шумом амплитуды ±330 (~-40 дБ) и обрубались при затухании
«активного окна». Субъективно: говорил — слышал шипение, закончил —
шипение догорало. Comfort noise удалён ПОЛНОСТЬЮ: пауза = чистая тишина
(silence-кадры с нулевым payload играются как есть). Браузерный клиент
этот шум никогда не генерировал — помехи были только в Qt.

**НОВОЕ (Qt+сервер): Opus-кодек через открытую библиотеку.** Голосовой
тракт переехал с raw PCM int16 (256 кбит/с на участника) на Opus
(32 кбит/с, чистый wideband-голос, устойчив к потерям):
- библиотека: opuslib_next (BSD-3-Clause) поверх libopus (BSD-3-Clause) —
  полностью открытый стек под permissive-лицензией, никакого
  самописного кодирования;
- кодек СОГЛАСОВЫВАЕТСЯ: клиент шлёт control-кадр
  {"t":"codec","codec":"opus"} внутри обычного FRVC-конверта, микшер
  отвечает подтверждением или отказом. Проводной протокол (кадры FRVC,
  auth-строка, TCP+1) ЗАМОРОЖЕН — старые клиенты v9.8/v9.9 работают
  с новым сервером как раньше;
- транскодирование в мосте: браузер по-прежнему едет на PCM int16 по

1. **Имперсонация отправителя** (критично): подпись X-Relay-Auth
   проверялась только в 3 из ~26 POST-маршрутов. Любой, знающий ключ
   доступа, мог править/удалять чужие сообщения, перезаписывать чужие
   аватарки и профили, слать DM и файлы от чужого имени. Теперь все
   POST проверяются централизованно; файловые загрузки — инкрементальным
   HMAC по телу (гигабайты не читаются в RAM); GET /dm/* — подпись
   path+query. Без подписи при включённом ключе — 403 (сервер без ключа
   работает как раньше).
2. **Path traversal в DM** (критично): `X-Relay-From: ../../evil` собирал
   путь файла диалога ВНЕ каталога dm/. Имена участников прогоняются
   через safe_name, мусорные — 400.
3. **Апдейтер**: манифест теперь поддерживает sha256/size — подменённый
   или битый exe не ставится; helper-bat делает бэкап .bak и откатывает
   старую версию, если новая не стартанула.
4. Устойчивость: лимит JSON-тел 2 МБ (раньше Content-Length: 10**9
   читался в RAM целиком, отрицательный — вешал поток), таймаут сокета
   30с (slowloris), атомарные записи settings.json/профилей/ботов/каналов
   (обрыв больше не обнуляет access_key и очки), кап чтения превью ссылок
   256К + семафор на 2 потока, чистка протухших сессий, клампы limit
   в историях, PNG-магия для аватарок + nosniff, secrets для кодов матчей.

- **Каналы живые**: сидя в канале, чужие сообщения/реакции/правки теперь

## v1.9.3 (v9.5) — аудит и багфиксы голосового чата (Qt + web)

**Задача: «проверить точно ли работает голосовой чат в QT и web версиях»
— прогнали реальный код обеих версий (Qt с мокнутым sounddevice, браузер
Chromium с фейковым микрофоном через WS-туннель) и починили найденное.**

Найдено и исправлено 5 багов (все подтверждены живыми тестами до/после):

1. **Голоса в web больше нет после 16 переподключений** (критично, обе
   версии): `VoiceMixer` никогда не удалял ушедших клиентов из списка,
   а лимит `_MAX_CLIENTS=16` считал и мёртвых. Каждое обновление
   страницы, ретрай сети или рестарт приложения сжигал слот навсегда —
   после 16 суммарных подключений сервер вечно отвечал `FULL`, голос
   умирал до перезапуска хоста. Теперь мёртвые чистятся при входе новых
   и в тик-цикле микшера (`tests/test_voice_fixes.py` гоняет 21 цикл
   вход/выход).
2. **Web-клиент не открывался вовсе при включённом ключе доступа**
   (критично, web): `GET /` (страница) требовал HTTP-заголовок
   `X-Relay-Key`, который браузер на обычной навигации послать не может
   — вместо интерфейса друг видел JSON `403 «неверный ключ доступа»`,
   хотя ключ вводится уже НА странице. Каркас (`/`, `/web`,
   `/static/*.js`) теперь открыт; все API-маршруты по-прежнему под
   ключом (проверено: `/voice/info` без ключа — 403).
3. **Голос в web рвался через ~5 секунд тишины/мьюта** (критично, web):
   WS-туннель `/voice/ws` создавал upstream-сокет с
   `socket.create_connection(timeout=5)` и не снимал таймаут — как
   только мост 5с не слал аудио (все молчат/замьючены), `recv` кидал
   timeout, pump умирал, браузер получал «соединение с голосовым
   мостом разорвано». Таймаут снят после подключения; проверено
   45-секундным простоем (2 цикла WS-пингов).
4. **Qt: диалог голоса залипал в «подключено» после разрыва** (Qt):
   если хост перезапускался/сеть мигнула, recv-поток умирал, но диалог
   продолжал показывать «Отключиться» и держать микрофон захваченным.
   Ошибки теперь маршалятся в GUI-поток через сигнал, диалог сам
   сбрасывает состояние и освобождает аудио-устройства. Штатный
   дисконнект (`_expected_close`) больше не порождает ложное
   «соединение разорвано».
5. **Состав канала в web врал** (web): список «кто в голосе» строился
   только из событий «говорит» — молчащие новички не появлялись, ушедшие
   оставались навсегда. Микшер теперь рассылает roster-событие
   `{"t":"roster","names":[...]}` при каждом входе/выходе (Qt его
   игнорирует — у него свой поллинг `/voice/participants`).

Прочее: мост не ловил `ConnectionClosed` из websockets ≥13 (не подкласс
`ConnectionError`) — резкий обрыв вкладки сыпал трейсбек в логи.

Тесты аудита (сверх существующих): реальный `VoiceClient` Qt с мокнутым
sounddevice — 12 проверок; `VoiceChannelDialog` offscreen против живого
сервера — 15; E2E Chromium (фейковый микрофон, ключ доступа, туннель) —
23 проверки, включая реальные плейаут-ворклеты (underflow-доказательство)
и mute/unmute без утечки. Регрессия: 300 OK / 0 FAIL по серверным тестам
проекта + `tests/test_voice_fixes.py` (10) — все существующие тесты
не тронуты (в `test_voice_speaking.py` только `read_control` научен
пропускать новые roster-кадры).

## v1.3.1 (v7.6) — рефакторинг и доработка общего чата

**Проверка выявила 8 проблем в общем чате (ChatScreen) — все исправлены.**

Баги:
- **Накопление растяжек в ленте.** Каждая перезагрузка ленты вызывала

# Что изменено

## Критический баг (найден, не был частью запроса, но ломал реакции и пины)

**Реакции и пины пропадали после перезапуска хоста.**
Сервер пишет реакции/пины/правки/превью как отдельные "дельта-события" в
`history.jsonl`, а в память подмешивает сразу. При старте сервера (`_load_history`)
переигрывались только правки текста — реакции и пины терялись, хотя в логе
были записаны честно.

Заодно нашлась вторая версия той же проблемы: подгрузка старой истории при
скролле вверх (`events_before`) для сообщений, вытесненных из кеша, читала
сырые события с диска без дельт и в обратном порядке — из-за чего пагинация
могла подвиснуть.

**Фикс:** `lib/relay_server.py` — единая функция переигрывания дельт
(`_build_delta_map` / `_apply_delta` / `_replay_deltas`), используется и при
старте, и при чтении старой истории с диска, и в новом `get_pinned_messages()`.

Файлы: `lib/relay_server.py`, `lib/constants.py`.

## 1. Предпросмотр ссылок

- Получение превью (`_fetch_link_preview`) вынесено из синхронного пути
  `add_text` в фоновый поток — раньше отправка сообщения с ссылкой могла
  зависнуть на до 5 секунд, ожидая ответ чужого сайта. Теперь `send_text`
  отвечает мгновенно, превью прилетает отдельным событием чуть позже.
- Добавлена защита от SSRF (`_is_safe_preview_url`) — сервер не полезет по
  ссылке из чата на localhost/внутреннюю сеть по IP.
- В `MessageBubble` теперь показывается og:image (грузится асинхронно), а
  ссылка кликабельна — открывается в браузере (`QDesktopServices`).

Файлы: `lib/relay_server.py`, `lib/constants.py`, `qt_app/widgets/message_bubble.py`.

## 2. Реакции на сообщения

- Клик по уже стоящей реакции теперь тоглит твою собственную (было доступно
  только через правый клик → меню).

Файлы: `qt_app/widgets/message_bubble.py`, `lib/relay_server.py`.

## 3. Пины сообщений (реализовано с нуля поверх существующего API)

# Итерация 3: drag-and-drop, приватность файлов в ЛС, удаление с витрины

## Главный корневой баг: drag-and-drop был мёртв во всём приложении

**Фикс:** вынес логику в один переиспользуемый компонент
`qt_app/widgets/drop_scroll_area.py` вместо трёх почти одинаковых копий
класса по разным экранам (это и было источником рассинхрона — где-то забыли
дописать, где-то не добавляли вовсе). Теперь используется в чате, ЛС и

Заодно: раньше при перетаскивании нескольких файлов разом отправлялся только

## Куда сохраняются файлы — как это устроено

Это не ссылки на раздачу, а честные копии байтов на диске **хоста** (у того,

## Самая серьёзная находка: приватность файлов в ЛС была фикцией

Перетаскивание/отправка файла в личные сообщения **не отправляла его
приватно** — файл летел в общую публичную витрину, видную всем на сервере,
а в самом окне ЛС не отображался вообще (не было кода для его рендера —
просто пустой пузырь без текста).

**Сделал полноценную приватную отправку:**
- Новая, физически отдельная от `files_dir` папка `dm_files_dir` на диске
  хоста.
- Новый эндпоинт `POST /send_dm_file` (аналог `/send_file`, но с получателем)
  и `GET /dm_download/<file_id>` — с проверкой прав: скачать может только
  отправитель или получатель, посторонний получает 403.
- Индекс приватных файлов восстанавливается из `dm/*.jsonl` при перезапуске
  хоста — файл можно скачать и после рестарта.
- В окне ЛС файлы теперь реально видны — компактная карточка с именем,
  размером и кнопкой скачивания (раньше такого рендера не было вовсе).

Проверено сквозным тестом: файл не виден в публичной витрине; получатель и
отправитель могут скачать; посторонний — не может; физическая изоляция папок
подтверждена; переживает перезапуск хоста.

Файлы: `lib/relay_server.py`, `lib/client.py`, `lib/storage.py`,
`lib/constants.py`, `qt_app/screens/dm_screen.py`.

## Побочная находка при отладке: вся история ЛС никогда не грузилась

При тестировании приватных DM-файлов всплыл отдельный, гораздо более
серьёзный давний баг: `/dm/history` и `/dm/conversations` были по ошибке
зарегистрированы внутри `do_POST`, а клиент всегда запрашивал их через GET
(это чтение данных, не действие — GET тут единственно правильный метод).
В итоге **любой** запрос истории ЛС или списка диалогов падал на 404
"неизвестный путь" в `do_GET`, а ошибка тихо проглатывалась в UI
(`_on_chat_error: pass`) — экран ЛС выглядел просто пустым, будто у вас нет
диалогов, даже если сообщения были отправлены и сохранены на диске.
Отправка (`/dm/send`, POST) работала всегда, поэтому проблема не была видна
сразу — переписка писалась на диск исправно, просто никогда не читалась
обратно.

**Фикс:** перенёс оба обработчика в `do_GET`, где им и место.

# Итерация 5: проверка автообновления для Qt

Модуль `lib/updater.py` (скачивание, сверка версий, замена exe) сам по себе
не привязан к UI-фреймворку и не трогался. Проблемы нашлись в том, как его
подключили в `qt_app/screens/settings_screen.py`.

## Критический баг: обновление физически не могло завершиться

`SettingsScreen` — не отдельное окно, а виджет, встроенный в
`QStackedWidget` внутри `MainWindow` (одна из вкладок). После скачивания
обновления код вызывал `self.close()`, рассчитывая закрыть приложение и дать
helper-скрипту (`.bat`, который ждёт исчезновения текущего процесса из
`tasklist`, затем подменяет exe и перезапускает) сделать своё дело.

Проверил экспериментально: `close()` на виджете, который не является
top-level окном, **не завершает процесс** — event loop продолжает жить как
ни в чём не бывало. Это значит, что helper-скрипт ждал бы завершения
процесса вечно, exe так и не подменялся бы, а статус в UI показывал бы
"Приложение закроется для обновления…" и... не закрывался. Автообновление
не работало ни разу, если дошло до этого шага.

**Фикс:** вместо `self.close()` теперь `QApplication.instance().quit()` —
явно завершает весь процесс, а не прячет один дочерний виджет. Проверил
контрастным тестом: со старым кодом (`close()` на встроенном виджете)
приложение через 2 сек всё ещё живо; с новым (`quit()` на `QApplication`)
`app.exec()` возвращает управление ровно на отметке ~2 сек, как и задумано.

## Захардкоженный чужой IP как дефолт для URL манифеста

Если `update_manifest_url` не задан в настройках, код подставлял
`http://100.123.45.67:8420/version.json` — похоже на тестовый адрес из
личной ZeroTier-сети того, кто портировал фичу на Qt. У любого, кто ни разу
не трогал этот параметр, приложение при проверке обновлений стучалось бы на
чужой адрес. В tkinter-версии (`lib/app.py`) дефолт — пустая строка
(проверка просто не выполняется, пока не настроено явно).

**Фикс:** дефолт — пустая строка, как в tkinter-версии. Если URL не задан,
статус явно говорит "Не задан URL манифеста обновлений", а не тихо
стучится куда-то.

## В Qt-версии не было поля, чтобы вообще настроить этот URL

В tkinter-версии есть текстовое поле "URL манифеста (JSON)" в настройках.
В Qt-версии такого поля не было совсем — единственный способ задать
`update_manifest_url` был вручную редактировать `settings.json` руками
на диске.

**Фикс:** добавил поле "URL манифеста обновлений" в форму настроек (рядом
с "Ключ доступа"), значение сохраняется сразу при нажатии "Проверить
обновления" (не только при подключении к серверу, как остальные поля).

Файлы: `qt_app/screens/settings_screen.py`.

## Проверено (итерация 5)

- `ruff check --select=F,E9` по всему проекту — чисто.
- `tests/qt_smoke_test.py` — проходит.
- Тест на реальном `SettingsScreen`: поле URL манифеста существует; при
  пустом поле и пустых settings дефолт больше не хардкоженный IP; после

- Контрастный тест, воспроизводящий старое поведение: `close()` на

# Итерация 6: как именно работает автообновление + GitHub Pages/ZeroTier/Tailscale

## Как это работает целиком (механизм)

1. **Манифест.** Обычный статический JSON-файл (`version.json`), лежащий
   где угодно, откуда виден по HTTP(S) — GitHub Pages, прямая ссылка на файл
   в GitHub Releases, Яндекс.Диск с публичной ссылкой, свой веб-сервер. Его
   URL вы вписываете в приложении: **Настройки → «URL манифеста
   обновлений»** (это поле я добавил в прошлой итерации — раньше в Qt его
   не было вообще). Никакой особой инфраструктуры манифест не требует, это
   просто "забрать JSON по ссылке".

2. **Приложение периодически (по кнопке "Проверить обновления") дёргает
   этот URL**, сравнивает поле `"version"` с версией приложения
   (`lib/constants.APP_VERSION`), и если на сервере версия новее — предлагает
   обновиться.

3. **Скачивание — с несколькими источниками и приоритетом.** Манифест может
   перечислить сразу несколько зеркал в `"download_urls"` (список, пробуются
   по порядку, пока одно не сработает) — **вот сюда как раз и кладётся
   GitHub Pages / GitHub Releases / любой другой публичный хостинг**.
   Дополнительно, если манифест указывает необязательное поле
   `"relay_file_id"` (id файла, загруженного в файловую витрину чьего-то
   постоянно работающего хоста в приватной сети), и вы **прямо сейчас**
   подключены именно к этому хосту — приложение сначала попробует скачать
   обновление напрямую через него, тем же самым каналом, что уже используется
   для чата. Раздача сама не знает и не заботится о том, ZeroTier это,
   Tailscale, Radmin VPN, обычный LAN или проброшенный порт — это просто
   HTTP-запрос на тот же `base_url`, к которому уже открыто соединение чата.
   Если приватный хост недоступен или файла там нет — молча откатывается на
   `download_urls` (публичные зеркала).

4. **Установка.** Новый `.exe` скачивается во временную папку, пишется
   `.bat`-хелпер, который ждёт завершения текущего процесса, подменяет
   старый exe новым и перезапускает — после чего приложение должно закрыть
   само себя (это и был баг из прошлой итерации).

## Нашёл и починил ещё один реальный баг: битый путь для приватного relay

`suggest_relay_download_url()` строила URL вида `{host}/file/<id>` — а на
сервере (`lib/relay_server.py`) зарегистрирован только `/download/<id>`.
Пути `/file/` не существует нигде. Это значит: "быстрый" путь через
локальный relay-хост (тот самый, что нужен для ZeroTier/Tailscale-сценария)
**всегда падал бы на 404**, даже если всё остальное было настроено
правильно. Заодно оказалось, что `preferred_file_id` в Qt-интерфейсе был
жёстко захардкожен как пустая строка с комментарием "можно добавить file_id
из чата" — то есть приватный путь ни разу не мог быть даже вызван, не то что
отработать.

**Фикс:**
- `/file/` → `/download/` в `suggest_relay_download_url`.
- Добавил в `UpdateInfo` и `check_for_updates` парсинг нового поля
  `relay_file_id` из манифеста — теперь это часть самого протокола
  обновления, а не то, что нужно откуда-то вручную прокидывать в код.
- В `settings_screen.py` `preferred_file_id` теперь берётся из
  `info.relay_file_id`, а не из хардкода.
- Переписал оба примера манифеста (`version.json`, `releases/version.json.example`)
  с исправленными путями и подробными комментариями, что и как заполнять
  для каждого сценария (публичный GitHub, приватный relay, оба сразу).

Файлы: `lib/updater.py`, `qt_app/screens/settings_screen.py`, `version.json`,
`releases/version.json.example`.

## Проверено (итерация 6)

Полный сквозной тест, эмулирующий именно тот сценарий, который вы описали:
- Статический HTTP-сервер на отдельном порту с `version.json` и `.exe` —

# Итерация 8: убрал кнопку, сделал вставку картинки по Ctrl+V

По вашей правке — кнопка "📷" не нужна и не то, что просили. Убрал её
полностью (вместе с логикой скрытия/восстановления окна и захвата экрана —
`qt_app/screenshot.py` удалён целиком). Вместо этого — вставка изображения
из буфера обмена прямо по Ctrl+V, как обычно работает после PrintScreen.

## Почему Ctrl+V с картинкой не работал раньше в принципе

Обычный `QLineEdit` (поле ввода сообщения) при вставке умеет **только
текст** — если в буфере обмена картинка, а не текст, `QLineEdit` её просто
молча игнорирует, ничего не происходит, никакой ошибки не показывается.
Так что дело было не в мелкой недоработке, а в том, что этот сценарий в
принципе не был реализован — обычное текстовое поле физически не умеет
вставлять изображения, это нужно перехватывать явно.

## Как сделал

Новый переиспользуемый виджет `qt_app/widgets/paste_image_line_edit.py`:
`PasteImageLineEdit(QLineEdit)` перехватывает `Ctrl+V` в `keyPressEvent`,
проверяет буфер обмена на наличие картинки (`mime.hasImage()`) — если она
там есть, вытаскивает `QImage`, шлёт как файл (тем же путём, что и
drag-and-drop, включая приватность в ЛС) и **не** пропускает событие дальше
в обычную текстовую вставку. Если в буфере не картинка, а обычный текст —
событие уходит в стандартную обработку `QLineEdit`, вставка текста работает
как раньше, ничего не сломано.

Поле ввода сообщения в обоих экранах (`chat_screen.py`, `dm_screen.py`)
теперь `PasteImageLineEdit` вместо обычного `QLineEdit`. В `dm_screen.py`
поле ввода имени в диалоге "Новый диалог" осталось обычным `QLineEdit` —
там вставка картинки не нужна.

Файлы: `qt_app/widgets/paste_image_line_edit.py` (новый),
`qt_app/screenshot.py` (удалён), `qt_app/screens/chat_screen.py`,
`qt_app/screens/dm_screen.py`.

# Итерация 10 (v1.3.0 / v70): фикс воксельного лобби 5v5 + привязка бота «Шахматы»

## Главный баг: кнопки «Заполнить ботами» и «Старт игры» не отвечали

**Причина:** `VoxelSessionServer.create_session()` / `VoxelEngine.__init__` брали
`max_players` по умолчанию = 8, но UI лобби по умолчанию предлагает команды
5v5 (`team_red_size=5`, `team_blue_size=5` → нужно 10 слотов). HTTP-эндпоинт
`/voxel/create` вообще не передавал `max_players`, поэтому лимит всегда
оставался 8, даже когда в UI были выставлены другие размеры команд.

При нажатии «Заполнить ботами» или «Старт игры» сервер пытался добавлять
ботов, пока обе команды не наберут нужный размер (`while team_count(...) <
team_*_size: add_bot(...)`). На 9-м игроке `add_player()` поднимал
`RuntimeError("session full")`. Это исключение никто не ловил — оно улетало
из `do_POST` необработанным, HTTP-хендлер падал посреди обработки запроса
**не отправив клиенту ответ**. Клиент (`urllib.request.urlopen`, timeout=3с)
просто получал таймаут/обрыв соединения, а `on_error=lambda _e: None` в
`voxel_game_dialog.py` тихо проглатывал ошибку — кнопка выглядела так, будто
ничего не произошло.

**Фикс** (`lib/games/voxel/engine.py`):
```python
self.max_players = max(max_players, team_red_size + team_blue_size)
```
Теперь слотов гарантированно хватает на обе команды, независимо от того,
кто и как создал сессию (HTTP `/voxel/create` или прямой TCP `join` до
создания сессии хостом). Дополнительно `fill_bots()`/`start_game()` обёрнуты
в `try/except RuntimeError`, чтобы даже непредвиденный edge-case не ронял
обработку запроса.

**Защита на будущее** (`lib/relay_server.py`): `do_POST`/`do_GET` теперь
оборачивают всю обработку в `try/except Exception`, которое при сбое всегда
отдаёт клиенту `500 {"ok": False, "error": "..."}` вместо тишины. Раньше
любая необработанная ошибка в любом эндпоинте (не только voxel) приводила
к точно такому же симптому — кнопка «не отвечает», ошибка нигде не видна.
Теперь такого больше не будет ни в одном эндпоинте.

Проверено: юнит-сценарий 5v5 (`create → fill_bots → start_game`) через
реальный `VoxelSessionServer` — добавляет ровно 10 ботов (5 red / 5 blue) и
переводит сессию в `playing` без исключений. 1v1 и другие размеры команд
тоже проверены.

## Привязка бота «Красивые Шахматы» (`!chess`)

Загруженный `chess_bot.py` был написан правильно по структуре (`ChessBot`
наследует `BaseBot`, реализует `matches_command`/`parse_command`/`get_meta`/
`process_command`/`get_help` — как `SnakeBot`/`OrbitalBot`), но не был
разложен по конвенции проекта и не был никуда подключён. Сделано:

- `lib/chess_bot.py` — серверная часть бота (без Qt-импортов, чтобы
  работало и на безголовом хосте): триггер `!chess`, статистика по ELO
  (`stats`, `result win/loss/draw`, `getscores` для топа), справка.
- `lib/chess_engine.py` — движок (`ChessEngine`) и ИИ (`ChessAI`, негамакс
  с alpha-beta) — чистая логика без Qt (с v1.3.2).
- `qt_app/widgets/chess_board_widget.py` — доска (`ChessBoardWidget`, миксины
  input/net/render + ядро), `qt_app/widgets/chess_piece_renderer.py` — рендер
  скинов фигур, `qt_app/widgets/chess_game_dialog.py` — композит `ChessGame`
  и `ChessGameDialog` — окно по образцу `SnakeGameDialog`/`OrbitalGameDialog`:
  доска слева, рейтинг ELO справа, результат партии (мат/пат) автоматически
  уходит на сервер и обновляет топ.
- Регистрация: `lib/relay_server.py:_register_default_bots()` +
  `qt_app/screens/chat_screen.py:_open_game_dialog()` — по инструкции из
  `docs/HOW_TO_ADD_BOT.md`, тем же способом, что и все остальные бот-игры.

**Побочная находка при подключении — шахматный движок был неиграбельным.**
В `_piece_moves()` для пешек направление хода было перепутано:
`d = 1 if white else -1`, хотя белые пешки стоят на `row=6` (доска хранится
как `a8..h1`, т.е. `row=0` — чёрная задняя линия) и должны идти к `row=0`,
то есть `d` должно быть `-1`. Из-за этого пешки не могли сделать ни одного
хода вперёд ни за одну из сторон — партия фактически не могла начаться
(в начальной позиции генерировалось 4 легальных хода вместо 20, только
кони). Исправлено на `d = -1 if white else 1`.

Проверено: в начальной позиции теперь 20 легальных ходов (было 4); ИИ против
ИИ отыграл 10 полуходов без ошибок с симметричным развитием фигур; детский
мат (Scholar's mate, 1.e4 e5 2.Qh5 Nc6 3.Bc4 Nf6?? 4.Qxf7#) корректно
распознаётся как мат.

**Важное ограничение, о котором стоит знать:** сейчас `!chess` — это игра
**против встроенного ИИ локально у каждого игрока** (как змейка/orbital), а
**не** парный сетевой матч между двумя людьми через relay. Оба человека
могут открыть `!chess` у себя и играть с ботом, общий рейтинг ELO виден всем
через `!chess top`, но partии друг с другом через сеть — нет. Чтобы сделать
настоящие сетевые шахматы 1×1 между людьми, нужен отдельный TCP session-
сервер по образцу `lib/voxel_server.py` (сессии, join по имени, синхронизация
ходов) — это отдельная по объёму задача, которую можно взять следующим шагом.

## Про «гранд-идею» ММ-режима (5v5 команды выбором до 1v1, карта побольше,
## туман войны, 15 раундов)

Она пока не реализована в коде — сейчас в воксельном шутере есть только:
настраиваемые размеры команд (1..10 на сторону) в лобби, PvE/PvP/Mixed
режимы, разрушаемые стены с настраиваемым HP. Фиксированное поле 900×700,
раундов/тумана войны/выбора размера карты нет.

Это самостоятельная по объёму фича (нужны решения по сетевому протоколу для
пере-конфигурации команд в лобби, производительности на большой карте,
расчёту видимости для тумана войны на каждого игрока, счётчику раундов и
респавну между ними) — сознательно не стал додумывать её за тебя вслепую в
этом же проходе, чтобы не наворотить поверх ещё один слой без понимания,
что именно нужно в первую очередь.
